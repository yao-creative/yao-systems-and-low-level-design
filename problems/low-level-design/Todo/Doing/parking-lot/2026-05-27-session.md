Yes, centralizing `park` and `unpark` at `ParkingLot` is the cleaner direction for this problem.

If you want the deeper formalization, think of the system as a state transition system:

1. global state = floors + spots + active tickets + vehicle-to-session occupancy
2. `park` and `unpark` are transition functions over that global state
3. the object that should own the public API is the one whose state boundary contains the full transition

So in a more logical sense:

- `ParkingSpot` owns only a local state fragment
- `Vehicle` is mostly an identity-bearing value in this workflow

That is why `ParkingLot` is the right system boundary. The decision is not "vehicle-focused vs lot-focused" in a business-language sense. It is about mutation closure:

> put the public operation on the aggregate that can apply the full state transition while preserving invariants

Here, `park` is not merely "set one spot occupied." It is something closer to:

```text
park(vehicle, lot_state) -> updated_lot_state + ticket
```

and `unpark(ticket, lot_state) -> updated_lot_state + fee`

Those are lot-level transitions, not spot-level transitions.

### 6C) (Interviewer)

Good question. Formalize extensibility as:

> a new requirement can be added by introducing a new variant or policy module, with limited change to already-correct core workflow code

So the test is not "can I edit the code and still make it work?" You can always do that. The test is:

1. where does the change propagate
2. how many existing methods must be modified
3. does the core state transition shape stay stable

In this parking lot problem, good extensibility means examples like:

1. adding a new vehicle or spot type without rewriting `park` and `unpark`
2. adding a new fee rule without rewriting ticket lifecycle logic
3. changing spot selection policy without rewriting occupancy correctness rules

So yes, enum augmentation plus `if/else` edits everywhere is usually a weak extensibility story, because the change axis leaks across many existing functions. A stronger design isolates the variable part behind a narrower boundary, while keeping the aggregate transition logic intact.
